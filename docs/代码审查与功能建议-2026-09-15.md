## 一、项目现状（我理解到的）

### 1.1 分层

```
Flutter  UI (pages/)  ── AnimatedBuilder(AppModel) ── 5 个页面 + 2 个查看器
   │
AppModel (全局单例, ChangeNotifier)       ← 原生事件唯一订阅者（转发 broadcast 流）
   │
CameraGateway (Dart 串行调度: 高优先级=可见单元格 / 低优先级=后台索引)
   │  ├ ThumbCache   两级缓存（内存 LRU 400 + 磁盘 300MB）
   │  ├ RecordStore  下载去重记录（JSON）
   │  └ SettingsStore
   │
NikonEngine（静态门面, MethodChannel + EventChannel）
   │
Kotlin  NikonsyncPlugin ── CameraEngine（单例，业务）── CameraProbes（探针）
                              │
                              └ PtpSession 接口
                                 ├ PtpIpClient  (Wi-Fi, TCP 15740 双通道, 分块/高速, 每块取锁)
                                 └ PtpUsbClient (USB,  bulk 整包读+余料, 全文件独占锁)
```

### 1.2 三条关键机制（改代码前必须知道）

| 机制 | 位置 | 含义 |
|---|---|---|
| 事务串行 | `PtpIpClient.txnLock` / `PtpUsbClient.txnLock` | PTP 命令通道同一时刻只能一个事务，所有并发都退化为"排队" |
| 非 OK 响应抛 `PtpException` | `PtpSession` 契约 | 相机**明确拒绝**不触发 USB 重枚举恢复（传输故障才恢复） |
| 超时即作废连接 | `PtpIpClient.doTransactLocked` | 一次 `SocketTimeoutException` → `streamDesynced` → 整条连接不可用 |

### 1.3 已经做得很好的地方（维持不动）

- `DragSelection` 把两个页面的滑动多选收敛成单一状态机（历史上就分叉出过 bug）。
- 失败计数 + `needsLoad()` 前置判断消灭了缩略图请求风暴。
- 取景帧的自调度循环 + `ValueNotifier` 隔离重建 + `cacheWidth` 解码。
- 探针与业务代码分离（`CameraProbes.kt` 443 行），破坏性探针有 `destructive` 标记 + 二次确认。
- 交接文档质量罕见：把"为什么这么改"和"踩过的坑"都写清了，本次审查的定位效率主要来自它。

## 二、问题清单

### A. 稳定性与正确性（建议优先修）

#### A1. USB 下载全程独占事务锁 → 保活/缩略图/详情全部饿死 🔴

- **位置**：`PtpUsbClient.getObjectToStream`（L431）用 `synchronized(txnLock)` 包住
  `downloadOnce` + `reopenAfterEnumeration` + `resumeWithPartial`，**整文件下载期间锁不释放**。
- **对比**：Wi-Fi 侧 `downloadChunked → writeChunk → doTransact` 是**每块才取锁**，块间释放，
  所以两个传输层对上层呈现的并发语义不同。
- **后果**（USB 下整卡同步 30GB ≈ 19 分钟）：
  1. `CameraEngine.startKeepAlive()` 的 5s `DeviceReady` 全部排队，保活实际失效；
  2. `notifyLinkDead` 走不到 → USB 真断线时 UI 仍显示"已连接"；
  3. Dart 侧 `CameraGateway` 里的缩略图/详情任务堆积，相册页全程转圈。
- **建议**：把"流式下载"提为一等公民——取锁只覆盖"发命令 + 读响应头"，数据相位按块读时
  在块之间释放锁；或让 USB 保活退化为"检查 `conn != null` + 最近 I/O 时间戳"而不发事务。
  最小改动版：保活在发现"有下载在跑"时跳过本轮，并记录下载心跳。

#### A2. `liveViewStart()` 吞掉失败并强制置位 🔴

- **位置**：`CameraEngine.kt` L843-853

```kotlin
runCatching { c.transactShort(OP_NIKON_LV_START, LongArray(0), 3000) }
    .onFailure { runCatching { c.transactShort(OP_NIKON_LV_START, LongArray(0), 8000) } }
liveViewOn = true
log("实时取景启动指令已发送（0x9201）")
return mapOf("ok" to true)
```

- **后果**：相机拒绝 0x9201（或两次都超时）时，UI 照常切到"实时取景"、
  `remote_page._waitingFrame` 永远显示"等待取景画面…"转圈，用户拿不到任何可行动信息。
  这与交接文档 §15 定下的原则（"启动取景失败不再被 runCatching 吞掉"）**自相矛盾**——
  那次修复只落到了探针 `probeLvFrames` 上。
- **建议**：把两次尝试的异常合并抛出（`IOException("实时取景启动失败：...")`）；
  `_switchMode` 已有 catch 会弹 SnackBar，无需再改 UI。

#### A3. 查看器字节缓存无上限 + 全分辨率解码 → OOM 风险 🔴

- **位置**：
  - `viewer_page.dart` L31 `final Map<int, Uint8List> _full = {}`（只增不减，每项 ≤40MB）
  - `local_viewer_page.dart` L34 `final Map<String, Uint8List> _bytes = {}`（同上）
  - `zoom_image.dart` L63 `Image.memory(bytes, ...)` **没有 `cacheWidth/cacheHeight`**
- **量化**：Z50 II JPEG L 为 5568×3712，解码成 RGBA ≈ **82MB/张**。连翻 10 张 =
  数百 MB 压缩字节 + 8 亿像素级位图 → 中低端机必然 OOM。
- **注**：`CameraGateway._viewMem` 有 4 项上限，但查看器自己的 map 把它旁路了。
- **建议**：① `_full/_bytes` 改 LRU（3~5 项）；② `ZoomableImage` 加按显示尺寸的
  `cacheWidth`（放大时另走一次高清解码）；③ 监听 `didHaveMemoryPressure` 主动清理。

#### A4. "取消下载"对大文件无效 🟠

- **位置**：`camera_gateway.downloadFiles` L186 `if (isCancelled?.call() ?? false) break;`
  只在**每个文件开始前**检查；`app_model.download` L354 传 `() => cancelRequested`。
- **后果**：用户在进度条上点"取消"，正在传的 4GB MOV 仍会传完（USB 下数分钟），
  UI 只有进度条消失；`DownloadSummary` 也不区分"取消"与"失败"。
- **建议**：把取消下沉到原生循环（`getObjectToStream` 的 chunk 回调里检查 → 抛
  `CancelledException` → 删除半成品文件），UI 文案区分"已取消（剩余 N 张未传）"。

#### A5. 8M/2M 缩放变体：方向信息丢失 + 内存峰值偏高 🟠

- **位置**：`CameraEngine.resizeJpeg`（L639-662）+ `download()` 的 `needResize` 分支（L692-701）
- **两个问题**：
  1. `createScaledBitmap` 输出的是**像素级已摆正的位图**，但 `bmp.compress()` 写出的新 JPEG
     **不带原 EXIF Orientation**。竖拍照片下载成 8M/2M 档后，用系统相册看是**横的**。
     原始档没有这个问题（原样落盘）。属于静默的数据质量缺陷。
  2. `inSampleSize` 只保证到长边 2 倍以内，最坏仍要解出约 4 千万像素（≈150MB 峰值，
     且原图与缩放图同时存在）。
- **建议**：用 `ImageDecoder.setTargetSize`（API 28+，minSdk 29 正好可用）一步到位；
  或缩放后用 `Matrix` 按原 Orientation 旋转再编码，并把 Orientation 标签写回/规范化。

#### A6. 一次超时作废整条连接，代价过高 🟠

- **位置**：`PtpIpClient.doTransactLocked` L463-474
- **现状**："明确作废 + 用户手动重连"确实优于静默错位，但触发面很宽：
  `liveViewFrame`（3s）、所有 `transactShort` 探针、保活排在长请求之后。
  交接文档 §15 遗留也承认这点（"目前只提示断开、需手动重连"）。
- **建议（两条低成本路线）**：
  1. 只读探针/取帧这类"相机可能不应答"的请求，**走独立的一次性命令连接**，不污染主通道；
  2. 超时后先尝试**轻量重连**（重开命令 TCP → 重做 InitCommand → `OpenSession` 容忍
     `SessionAlreadyOpen`）——协议上允许，能把"用户操作"降级为"自动恢复一次"。

### B. 性能与体验

#### B1. 每次 `notifyListeners` 都重算筛选 + 排序 🟠

- **位置**：`gallery_page._onModelChanged`（L81-85）无条件 `_filteredCache = null`。
- **放大因素**：`AppModel._notifyThrottled` 是 150ms 节流，而索引期间（每完成一个文件）
  与下载期间（原生 300ms 一次进度）都在通知 → 5000 张的卡，等于每 150ms 排一次 5000 项，
  外加全页重建（`AnimatedBuilder(animation: model)` 在每个页面 root）。
- **建议**：缓存失效条件收紧为"`files` 身份/长度 + `sortMode` + 筛选值"变化的指纹比较；
  更彻底的做法是把"索引进度""下载进度"拆成独立 `ValueNotifier`，让网格不订阅它们
  （`SettingsPage` 冻结 `DebugPanel` 实例已经是同一个思路的局部解）。

#### B2. `_indexStep` 的"每 16 个通知一次"是失效的 🟠

- **位置**：`app_model.dart` L323

```dart
if (files.length % 16 == 0 || indexingDone) notifyListeners();
```

- **问题**：`files.length` 是**列表总长度（常量）**，不是索引进度计数。对 1500 张的卡
  `1500 % 16 = 12` → 恒为 false；对 1600 张的卡 → **每个文件都通知一次**。
  目前进度条之所以看起来正常，靠的是相册页可见单元格 `ensureLoaded` 的副作用回调。
- **建议**：改成按已索引计数（`indexedCount % 16 == 0`）或直接改用 `_notifyThrottled()`。

#### B3. 排序语义不一致 🟡

- **位置**：`gallery_page._computeFiltered` L99-120
- `newest` 的 `default` 分支用的是"文件夹倒序 + 句柄倒序"，**完全没用 `dateRaw`**；
  `oldest` 却用 `dateRaw` 且未索引项排最后。
- **后果**：同一列表切"最早优先"时顺序整体跳变；跨文件夹时"最新优先"并不按时间。
- **建议**：统一为"优先 `dateRaw`，缺失回退 folder+handle"，并保证两个方向严格互为镜像。

#### B4. "一键下载"的数量在索引完成前会虚高 🟡

- `isDownloaded` 需要 `name + size`，详情未读到一律按"未下载"计（`_taskBar` 的 `pending`）。
- **后果**：确认框说"N 张"，实际会跳过很多（对话框虽写了"会自动跳过"，但数字对不上会被怀疑）。
- **建议**：文案区分"待确认 N 张（其中 M 张详情未读）"，或在索引进度未完成时先给区间。

#### B5. 拖动选择的命中测试是 O(n) 逐格扫描 🟡

- `gallery_page._hitIndex`（L171-181）与 `downloads_page._hitIndex`（L85-96）都在每次
  `onPointerMove` 遍历整个列表。分组视图下相册页会退化为逐格（注释已说明原因）。
- **建议**：分组视图改用"section 累计高度前缀表 + 二分"；手机页可缓存"key → Rect"。
  记录数上万时这是明显掉帧来源。

#### B6. `_cellKeys` / `_thumbs` 无回收 🟡

- `gallery_page._cellKeys`（GlobalKey）与 `downloads_page._cellKeys/_thumbs` 都只增不减；
  换卡或删除记录后条目仍留在 map 中（虽未挂载，仍持有对象引用）。
- **建议**：列表刷新后按当前主键集合裁剪。

### C. 工程化与文档

#### C1. 原生已有能力没有 UI 入口 🟠

- `NikonEngine.protectObject(handle)` 已封装（`nikon_engine.dart` L82-83），
  原生 `CameraEngine.protectObject(0x1012)` 也已实现——**全项目没有任何调用点**。
  对比 `deleteObject` 已被"下载后删除"用上。
- 详见功能建议 **F1**（这是性价比最高的一条）。

#### C2. Manifest 声明了"插上相机自动拉起"，但没有代码处理 🟡

- `AndroidManifest.xml` L51-57 声明了 `USB_DEVICE_ATTACHED` + `device_filter.xml`（VID 1200），
  但 `MainActivity` 没有 `onNewIntent`，插件里也没有 attach 广播接收者。
- **后果**：插上相机 → App 被拉起 → 停在连接页什么也不做（用户以为坏了）。
- **建议**：实现"插入即提示/自动连 USB"（见 F9），或删掉这段声明。

#### C3. `KeepAliveService` 的三处小问题 🟡

- 通知图标用的是 `android.R.drawable.stat_sys_data_bluetooth`（蓝牙图标，语义错误，L40）。
- `POST_NOTIFICATIONS` 只在 Manifest 声明，**代码里从未运行时请求** → Android 13+ 上前台
  服务通知不可见（用户不知道后台在跑），"下载进度通知栏"（交接文档 §11 待办）也依赖它。
- `cpuLock.acquire(4h)` 到期自动释放但服务仍在前台 → 长会话后段失去 CPU 保活。

#### C4. dead code / 冗余字段 🟡

| 项 | 位置 | 处理 |
|---|---|---|
| `CameraFile.dedupKey()` | `camera_file.dart` L51 | 无调用（`RecordStore` 自己拼 key）→ 删 |
| `ThumbCache.clearMemory()` | `thumb_cache.dart` L64 | 无调用 → 删或接到换卡/内存压力 |
| `AppModel.engine` 字段 | `app_model.dart` L51 | `NikonEngine` 全是静态成员，实例化无意义 → 删 |
| `enumerate()/objectInfo()/getThumbnail()/capabilities()` | 仅调试面板使用 | 保留，但在 `nikon_engine.dart` 注明"仅调试" |
| `NikonEngine.probeLiveView/2/3/4/5` | 调试面板 | 5 个历史探针并列，建议在 `_Probe` 表里合并分组（旧探针标注"已被 X 取代"） |

#### C5. `build_apk.bat` 第 7 行的路径被写坏了 🟡

- 实测文件字节：`echo APK 位置: %~dp0build<0x07>pp\outputs\flutter-apk<0x07>pp-debug.apk`
  （`\a` 被写成了 0x07 BEL 控制字符，`build\app` / `\app-debug.apk` 两处都坏了）。
- 双击运行后打印的路径是错的（还带控制字符）；且两个脚本**只编 debug**，
  与交接文档 §3 强调的"装机必须用 release + 递增 versionCode"完全脱节。
- **建议**：修好 echo 行；给脚本加 `release` 参数并把 `--build-number` 从环境变量/
  自增文件取（见 C6），把文档里的装机构建固化进脚本，避免每次手敲。

#### C6. 版本号语义被安装问题绑架 🟡

- `pubspec.yaml` 已是 `1.0.0+2027`，纯粹为了绕 `INSTALL_FAILED_VERSION_DOWNGRADE`
  （交接文档 §3/§17.1 都记录了这段插曲）。
- **建议**：pubspec 回到语义版本（如 `1.1.0+3`），装机版本号走命令行 `--build-number`，
  并由 `build_apk` 脚本维护一个 `.build_number` 自增文件。这样源码版本与安装版本解耦。

#### C7. 文档与实现已经明显偏离 🟡

- `docs/技术方案.md` §3 写的是 **Riverpod + go_router + drift**，实现是
  `ChangeNotifier` + `Navigator` + JSON 文件；§1 写"本期不做删除相机文件"，
  但删除/保护/下载后删除都已实现。
- **风险**：下一个 AI 会照着 drift 去找数据库。
- **建议**：在 `技术方案.md` 顶部加一节"实现与方案的差异（2026-09-15）"，逐条列出并
  标注哪一个是最终决定（例如"记录层用 JSON 是刻意选择：数据量小、无查询需求"）。

#### C8. 测试与 lint 🟡

- 全项目 2 个测试文件，其中 `widget_test.dart` 是 `expect(true, isTrue)` 占位。
- `analysis_options.yaml` 只 include 默认 `flutter_lints`，无项目自定义规则。
- **建议（按性价比排序）**：
  1. `DragSelection` 单测（锚点范围、方向反转、`toggleAll` 与 `prune` 的语义）——
     这两块历史上都出过 bug；
  2. `RecordStore.load` 的旧格式兼容（`name:size` / `name#variant:size`）；
  3. 相册筛选+排序的纯函数测试（抽成顶层函数即可测）；
  4. 补 `flutter analyze --fatal-infos` + `dart format --set-exit-if-changed` 到提交前检查。
- **结构前提**：`AppModel` 是全局单例、依赖 `static NikonEngine`，无法注入假引擎。
  把 `NikonEngine` 抽成接口（如 `PtpEngine`）注入是让上面 1~3 可测的前提。

## 三、高价值功能建议（按"贴合现有设计逻辑"排序）

每条都标出**能直接复用的既有能力**——这是判断成本的关键。

### 优先级矩阵

| 功能 | 价值 | 成本 | 复用的既有能力 |
|---|---|---|---|
| F1 相机端文件管理 UI（删除/保护） | ★★★★ | ★ | 原生 `deleteObject`/`protectObject` 已完成，Dart 侧已封装 |
| F2 间隔拍摄 / 延时摄影 | ★★★★★ | ★★ | `capture()`（AF 驱动+忙重试+8s 预算）、`objectAdded → _onNewPhoto`（含"读走新照片解锁快门"）、`model.download` |
| F3 自动同步（边拍边传）+ 通知栏进度 | ★★★★★ | ★★★ | `ObjectAdded` 链路已通、`KeepAliveService` 前台服务已在跑、去重记录已具备 |
| F4 存储卡剩余容量 / 可拍张数 | ★★★★ | ★ | 只需新增 `GetStorageInfo(0x1005)`，UI 位置已在 `_taskBar` |
| F5 RAW+JPEG 成对识别与配对下载 | ★★★★ | ★★ | `listFolders` 已给文件名+文件夹，只需在 `_computeFiltered` 前分组 |
| F6 视频在线预览/播放 | ★★★ | ★★★ | USB 27.1MB/s 已让"先拉完再播"可行 |
| F7 参数面板扩展（曝光补偿/白平衡/驱动模式）+ 构图辅助 | ★★★★ | ★★ | `propDescFull`/`setShotParam` 通路完全通用，只需加码表项 |
| F8 评分标记 / 分享导出 / 按日期归档 | ★★★ | ★ | `RecordStore` JSON 可平滑扩字段，SAF `RELATIVE_PATH` 已按类型分 |
| F9 USB 插入即连 | ★★★ | ★ | Manifest 已声明，缺的只是 attach 处理 |
| F10 下载队列持久化 + 跨次断点续传 | ★★★★ | ★★★ | USB 单次续传已实现，需把半成品先落私有目录 |

### 重点推荐（前四个）

#### F1. 相机端文件管理 UI —— 能力已就绪，只差一个入口

- 现状：相册页选择栏只有"下载"。`_confirmDanger`（设置页）已经提供了
  "危险操作 + 二次确认 + 常驻提示"的交互范式，可直接复用。
- 落点：选择栏加"删除相机文件 / 保护 / 取消保护"；分组头部（按天）支持"整组保护"。
- 价值：现场挑片（保护 = 回相机后不会被误删）、卡满时不必拔卡。
- 注意：`deleteObject` 是不可逆操作，必须复用"下载成功后再删"的校验顺序，
  绝不能先删后传（`downloadFiles` 里已是这个顺序，照抄即可）。

#### F2. 间隔拍摄 / 延时摄影 —— 遥控页的自然延伸，也是最大的差异点

- 复用：`capture()` 已经处理了最难的几件事（对焦优先机型的 AF 驱动 + 长间隔忙重试 +
  8s 预算 + SDRAM 待取图像探测 + `capturePhase` 阶段上报）；
  `_onNewPhoto` 里"全量读取新照片以解锁下一次快门"正是连拍/间隔拍摄的**前置条件**。
- 新增：一个参数面板（张数 / 间隔 / 首拍延迟 / 拍后是否自动下载 / 是否只在取景模式下拍）、
  一个 `Timer` 调度器 + 停止条件、进度显示（已拍 N/M、下一张倒计时）。
- 价值：SnapBridge 做不到；对风光/星空/会议记录场景是刚需；顺带把 §7.1 的
  "连拍卡忙"假设在真机上验证透。
- 风险：`CAPTURE_BUDGET_MS = 8s` 是按单张设计的，间隔 < 10s 时需要重新分配预算；
  相机写卡间隙要留余量（建议最短间隔 3s 起步并给提示）。

#### F3. 自动同步（边拍边传）+ 通知栏进度 —— 技术方案里承诺过的核心场景

- 复用：`ObjectAdded` 在全链路上已经通了（标准事件通道 + 0x90C1 排水 + 遥控路径实测
  正常到达）；`KeepAliveService` 已经在前台跑，升级为"同步服务 + 通知进度"即可；
  `POST_NOTIFICATIONS` 已声明（补一次运行时请求，见 C3）。
- 规则建议：仅 JPEG / 是否含视频 / 最小文件大小 / 只传本次连接后的新增；
  去重交给现有 `RecordStore`。
- 价值：**"按下快门数秒内自动入库"，且传的是存储卡原图**——这是与 SnapBridge
  只传 2MP 小图的根本差异，也是最初技术方案 §4.4 的卖点。

#### F4. 存储卡状态 —— 一行协议换来一屏信息

- 现状：连接页只显示电量与照片数；待下载条已经会算"还差 N 张"，但没有容量概念。
- 新增 `GetStorageInfo(0x1005)` → `MaxCapacity / FreeSpaceInBytes / FreeSpaceInImages`，
  展示在连接页与 `_taskBar`："卡剩余 42.3GB · 还可拍 1180 张"。
- 顺带在"一键下载"确认框里给出时长估算（已有实测速率：USB 27.1MB/s，Wi-Fi 2.4MB/s）。

### 其余推荐（一句话）

- **F5 RAW+JPEG 成对**：同 stem 折叠为一格（角标 ×2），长按选"仅 JPG / 仅 NEF / 两者"，
  "一键下载"默认只下 JPEG。摄影师价值极高，实现只是分组。
- **F6 视频在线播放**：本地视频目前只能跳系统播放器；USB 27MB/s 下"先拉完再播"
  200MB 约 7s，完全可行。更轻的版本：显示时长 + 关键帧预览。
- **F7 参数面板扩展**：`propDescFull` 已经把枚举表/范围/可写标志全解析出来了，
  `setShotParam` 的 data-OUT 通路也通——加曝光补偿/白平衡/驱动模式只是往
  `PropDialect` 里加码（Wi-Fi 方言码待"属性码Dump"确认）。再加取景网格线/水平线/峰值对焦。
- **F8 评分与导出**：`RecordStore.fromJson` 有默认值兜底，加字段是平滑的；
  本地页加星级筛选 + 系统分享（发微信）。
- **F9 USB 插入即连**：补齐 attach 处理，让"插上就同步"成立（与 C2 同一条）。
- **F10 队列持久化**：目前中断会删除半成品，所以**无法跨次续传**。改成
  "先落 app 私有目录 → 完成后搬进 MediaStore" 是"30GB 整卡同步"可用的前提，
  也是"失败可重试"（现在失败只弹一句 SnackBar，没有重试入口）的基础。

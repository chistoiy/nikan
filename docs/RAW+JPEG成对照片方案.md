# RAW+JPEG 成对照片：显示 / 下载 / 筛选方案（已采用方案 A）

> 状态：**方案 A 已实现**（APK 2037）。实现要点与一处简化说明见本文末尾「§7 实现说明」。
> 相关代码：`lib/models/camera_file.dart`（文件模型）、`lib/pages/gallery_page.dart`（相册）、
> `lib/pages/widgets/gallery_filter_bar.dart`（筛选条）、`lib/engine/camera_gateway.dart`（下载与去重）
> 与 `lib/app_model.dart`（配对索引）。

## 1. 问题是什么

相机打开「RAW + JPEG 同时记录」后，同一张照片会生成两个对象：

```
100NZ502/DSC_1234.JPG   24.6 MB   ← JPEG（可直接看）
100NZ502/DSC_1234.NEF   51.2 MB   ← RAW（有缩略图，但手机看不了原图）
```

它们是**两个独立的 PTP 对象**（句柄不同），只是文件名基名相同、大小不同。
现状（不处理）会带来三个具体问题：

1. **相册里每一张照片看到两条**，1545 个文件里有成对的话，列表长度直接翻倍，挑图很难受。
2. **"下载"容易下一半**：用户想收图，勾了 JPEG 就完了，或者误勾两个、白花一倍的流量和时间
   （Wi-Fi 1.5MB/s 下 NEF 51MB 要 34 秒）。
3. **筛选按类型切会把成对拆开**：现在筛选条有 全部/JPEG/RAW/视频，选 JPEG 就看不到配套的 RAW，
   用户无法用"我要这对"这种意图挑图。

## 2. 需要真机确认的三件事（动手前先跑一次探针）

写代码前必须先验证，否则可能基于错误前提设计：

| 待验证 | 怎么验 | 影响 |
|---|---|---|
| 成对文件的 `Filename` 是否严格同基名（大小写、后缀 NEF/NRW） | 「快速枚举 + ObjectInfo」按同名基名分组统计 | 决定配对键 |
| 是否同目录、句柄是否相邻 | 同上，打印目录与句柄 | 决定"是否只需看邻居" |
| 相机是否提供"RAW+JPEG"关系属性（如 `0xD1xx`） | 属性码 Dump 里查找，或 `0x90CA GetVendorPropCodes` 后逐个读 | 有就直接用相机的答案，没有才靠文件名配对 |

> 依据：`CameraFile.kind` 目前是 `isVideo / isJpeg / 其余算 raw` 推出来的，
> 而 `isJpeg` 来自 ObjectInfo 的格式码。**没有**任何"成对"信息，配对必须自己算。

## 3. 三个方案

### 方案 A（推荐）：一条一文件，但加"成对标记 + 联动选择"

保留现在的"一个对象 = 一个条目"模型，只加三件事：

1. **配对识别**：基名 + 目录相同的 JPG/NEF 视为一对（枚举完成后一次性算好，O(n)）。
2. **网格显示**：成对的条目右上角加 `R+J` 角标；已下载角标分列显示（`J✓` / `R✓`），
   让用户一眼看出"这张的 RAW 还没收"。
3. **联动选择**：勾选任一条时自动勾上它的配对（设置里可关，**默认开**），
   用户仍可单独取消其中一个（取消后再点同一条不会又被自动带上）。
4. **下载画质选项扩展**（现在只有 原图/8M/2M）：
   - `JPEG 原图`（默认）
   - `RAW`
   - `RAW + JPEG`（成对一起下）
   - `8M` / `2M`（缩放，仅 JPEG）

   → 选择"RAW + JPEG"时，成对的两条一起排队；不成对的 RAW/JPEG 各自照常。

- **优点**：不动数据模型，不动枚举/索引/去重/续传的既有逻辑，回归面最小；
  用户仍能只挑 JPEG（现场挑片最常用）；成对信息对新加的"日期分组"完全兼容。
- **成本**：中。改动集中在 `CameraFile`（加 `pairHandle` 字段）、`gallery_page`（角标+联动）、
  `gallery_filter_bar`（画质选项 + 一个"只看成对"筛选）、`camera_gateway`（按对排队）。

### 方案 B：合并成"一张照片（两个文件）"卡片

列表里成对的两个文件显示为**一个**条目，点开是一个小面板：

```
DSC_1234                    [R+J]
 ├ JPEG  24.6 MB   ✓ 已下载
 └ RAW   51.2 MB   ○ 未下载   [下载 RAW]
```

- **优点**：列表短一半，最符合"这是一张照片"的直觉。
- **缺点**：`CameraFile` 要从"一个对象"变成"一个对象 + 可选配对"，
  **枚举、索引、缩略图缓存、去重记录、选择状态、拖动多选、日期分组**全都要跟着改；
  拖动多选按矩形命中网格坐标，条目变一对后命中逻辑也要重做。
  回归面很大，而收益主要是"列表更短"。
- **成本**：高（估计是方案 A 的 3 倍以上）。

### 方案 C：不动 UI，只改默认行为

下载时如果勾了 JPEG，自动把配对 RAW 一起下。

- **优点**：改动最小。
- **缺点**：违背"用户勾了什么就下什么"的直觉，可能悄悄多下 51MB；
  Wi-Fi 下这是 34 秒的额外等待，用户会以为卡住了。**不推荐**。

## 4. 建议

**选方案 A**。理由：

1. 成对信息是"派生属性"，天然适合算好挂在条目上，而不是重构模型；
2. 现场挑片时"只要 JPEG"是主流需求，方案 A 支持，方案 B 反而多一层点击；
3. 与已有的**日期分组 + 拖动多选 + 未下载筛选**都能直接叠加（这些能力已经实现，
   见 `gallery_page.dart` 的 `_groupedGrid` / `DragSelection` / `undownloadedOnly`）；
4. 万一配对识别有误（比如同基名的两张不同照片），方案 A 的失败是"角标错了"，
   方案 B 的失败是"有一条照片看不见了"——后者更严重。

## 5. 边界与风险（方案 A 下要处理的）

| 情况 | 处理 |
|---|---|
| 只有 JPEG 没有 RAW | 不显示成对标记，照常 |
| RAW 是 NRW/NEF 两种后缀 | 后缀表 `{JPG, JPEG, NEF, NRW}` 统一识别 |
| 连拍同号不同目录 | 配对键必须带目录，不能只看文件名 |
| 配对大小差很多（RAW 51MB） | 下载对时进度条按"两张文件"计入总数，避免"怎么还在传"的错觉 |
| 去重记录 | 沿用现有 `name:size` 键，天然区分 JPEG 与 RAW，不需要改 |
| 用户只要 JPEG 的 RAW 兄弟 | 联动选择可关；取消单条后不再自动带上 |

## 7. 实现说明（APK 2037 已落地）

| 方案要点 | 实现 |
|---|---|
| 配对识别 | `CameraFile.pairKey = 目录 + 大写基名`；`AppModel._pairIndex` + `_pairOne()`（**类型必须互补**：一个 JPEG 一个 RAW，否则不配对——宁可不连也不要连错） |
| 何时配对 | 快速枚举后 `_rebuildPairIndex()` 全量重建；索引每个文件补全详情后 `_pairOne()` 增量配对（O(1)） |
| 网格标记 | 右上角 `R+J`；左下角下载状态改为 **J / R 分列**（实心绿勾=已下载，空心灰圈=未下载） |
| 联动选择 | 统一放在 `DragSelection.onChanged` → `_syncPairs()`，双向同步（选中带配对、取消也带配对）；设置项 `linkRawJpegPairs` 默认开 |
| 筛选 | 筛选条新增「成对 N」chip（只看有配对的照片）；与「按天分组」「未下载」「类型」可叠加 |
| 下载 | **未新增档位**：勾选即联动成对下载（等于"RAW+JPEG"）；只要 JPEG → 关掉联动或用 JPEG 筛选；只要 RAW → 关掉联动或用 RAW 筛选 |

**为什么没有加 `RAW` / `RAW+JPEG` 两个画质档**：画质档位（原图/8M/2M）解决的是
"同一个 JPEG 存多大"，而"要不要 RAW"是**选哪些文件**的问题。把两个维度塞进同一个下拉会
产生 4×3 的组合语义（"8M + RAW" 到底是缩放的 RAW 还是原图 RAW？），用户与实现都会糊。
用联动选择 + 类型筛选表达同一件事，语义更单一，也不会让 `variant` 出现在去重键
（`name#variant`）里污染已下载记录。

**待真机验证**：成对文件是否严格同基名（大小写、NEF/NRW 后缀）——本实现按"目录 + 大写基名"配对，
若相机用了别的命名规则（例如连拍后缀不同），角标不会出现（安全的失败方向：不配对，而不是配对错）。
